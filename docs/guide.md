## 1. Что это за продукт

Тренажёр проводника ВСМ. Проводник проходит ситуации в вагоне («сценарии»): читает описание, выбирает действие,
видит реакцию пассажиров и изменение двух шкал — **лояльность пассажиров** и **рейтинг безопасности** (0–100).
Некоторые шаги критические — на них тикает таймер; если не успеть, срабатывает отдельная ветка «время вышло».
После финала — подробный разбор: что выбрано, как изменились шкалы, почему и как было правильно.

Поверх этого — геймификация: результат рейса, опыт, уровни, достижения, рейтинг, уведомления; оценки
компетенций и рекомендация следующей тренировки. Методист редактирует сценарии в редакторе без программирования.

Две роли: **проводник** (проходит сценарии) и **методист** (плюс редактор и справочник сотрудников).

## 2. Технологии

| Слой | Технология | Где |
|---|---|---|
| Фронтенд | React 18 + TypeScript + Vite, React Router | `frontend/` |
| Бэкенд | Python 3.12, FastAPI, Pydantic | `backend/app/` |
| База | PostgreSQL 16, SQLAlchemy 2, миграции Alembic | `backend/migrations/` |
| Тесты | pytest (бэкенд), Vitest (фронтенд) | `backend/tests/`, `frontend/src/**/*.test.ts` |
| Запуск | Docker Compose: postgres + backend + frontend (nginx) | `docker-compose.yml` |

Внешних платных сервисов и библиотек UI нет: вся графика — свои SVG и CSS.

## 3. Как всё связано

```
Браузер ──/api/...──> nginx (frontend-контейнер) ──> FastAPI (backend) ──> PostgreSQL
          SPA-файлы <──┘
```

- Браузер всегда ходит на **свой же адрес** с префиксом `/api`. В Docker это проксирует nginx
  (`frontend/nginx.conf`), при разработке — Vite (`frontend/vite.config.ts`). Префикс `/api` при этом срезается:
  сам бэкенд обслуживает `/attempts`, `/auth/login` и т. д.
- Благодаря одному адресу cookie сессии «свои», CORS не нужен.
- Бэкенд не хранит состояние в памяти: сессии, попытки, награды — в базе. Поэтому его можно запускать в нескольких
  экземплярах.

## 5. Сценарий: из чего состоит

Сценарий — JSON-файл в `backend/app/scenarios/data/` или запись, созданная в редакторе. Внутри — граф:

```json
{
  "initial": {"loyalty": 60, "safety": 80},          // стартовые шкалы
  "flags": {"was_rude": false},                       // «память» попытки: что игрок сделал раньше
  "awards": [{"achievement": "diplomat", "when": {...}}],
  "visual": {"characters": {"man": {...}}},           // персонажи сцены (необязательно)
  "start_node": "start",
  "nodes": {
    "start": {
      "text": "описание ситуации",
      "timer_seconds": 20,                            // есть — шаг критический
      "timeout": { "effects": {...}, "next_node": "..." },   // что будет, если время вышло
      "debrief": "как лучше поступить (для разбора)",
      "visual": { "speaker": "...", "moods": [...], "props": [...] },
      "choices": [
        {
          "id": "calm",
          "text": "текст кнопки",
          "condition": {...},                         // показывать, только если…
          "effects": {"loyalty": 5, "safety": 0},     // изменение шкал
          "set_flags": {"calm_approach": true},
          "assessment": {"communication": 2},         // оценка решения по компетенциям
          "explanation": "почему так (для разбора)",
          "next_node": "suitcase"                     // или "transitions": [...]
        }
      ]
    },
    "end_calm": {"text": "...", "is_ending": true, "ending_summary": "...", "outcome": "calm_resolution"}
  }
}
```

**Условия** — маленький язык в JSON (без `eval`):
`{"flag": "was_rude"}`, `{"scale": "loyalty", "op": ">=", "value": 70}`, `{"all": [...]}`, `{"any": [...]}`,
`{"not": ...}`. Их вычисляет функция `evaluate` в `backend/app/scenarios/conditions.py`.

**Условные переходы** (`transitions`) — список «если условие → узел»; берётся первый подходящий, последний — без
условия (по умолчанию). Так финал «Места у окна» зависит от флагов резкости и порогов шкал.

Сейчас три сценария: «Конфликт из-за откинутого кресла» (разминка), «Место у окна» (13 узлов, 3 финала),
«Пассажиру стало плохо» (9 узлов, 3 финала). Тексты опираются на материалы кейса.

## 6. Движок: что происходит при нажатии на вариант

Файл `backend/app/scenarios/engine.py`, класс `ScenarioEngine`. Главный метод — `apply_choice`. По шагам:

1. **Проверки.** Попытка не завершена; `expected_step` из запроса совпадает с текущим номером шага — иначе ошибка
   `step_mismatch` (защита от двойного клика и устаревшей вкладки).
2. **Таймер.** Если у узла есть таймер и `now ≥ deadline` (дедлайн = время показа узла + `timer_seconds`) —
   применяется ветка `timeout`, присланный выбор игнорируется. Если игрок прислал «пусто» (`choice_id: null`)
   раньше дедлайна — ошибка `timer_not_expired`.
3. **Поиск варианта.** Ищется только среди **видимых** вариантов (их `condition` истинно на текущем состоянии).
   Скрытый и несуществующий вариант дают одинаковую ошибку — чтобы нельзя было выведать скрытые ветки.
4. **Оценка компетенций** (`_assess`): для каждой компетенции «набрано» = балл выбранного варианта, «максимум» =
   лучший балл среди видимых вариантов. Копится в `attempt.assessment`.
5. **Эффекты.** Прибавляются к шкалам, каждая шкала ограничивается 0–100. Сохраняется *фактическое* изменение.
6. **Флаги** из `set_flags`.
7. **Следующий узел** (`_next_node`): `next_node` или первый подходящий `transitions` — проверяется уже **после**
   эффектов и флагов.
8. Номер шага +1, запоминается время показа нового узла (новый таймер стартует сейчас). Если узел — финал,
   попытка завершается.

Метод `expire_if_due` делает шаг «время вышло» при обычном чтении попытки — так страница, открытая заново после
дедлайна, показывает реальный исход.

Движок ничего не знает про HTTP и базу — только про граф и объект попытки. Поэтому его легко тестировать
(`backend/tests/test_engine.py`).

## 7. Сервис попыток и защита от гонок

Файл `backend/app/services/attempts.py` — связывает HTTP, движок и базу.

- `start_attempt` — создаёт попытку и кладёт в неё **снимок** графа, название и версию сценария. Дальше движок
  читает только снимок: если методист опубликует новую версию, начатая попытка этого не заметит.
- `submit_choice` / `get_attempt`:
  1. читают попытку с блокировкой строки (`SELECT … FOR UPDATE`) и только свою (`_lock_attempt` фильтрует по
     сотруднику — чужая попытка выглядит как «не найдена»);
  2. вызывают движок;
  3. если попытка завершилась — начисляют награды (`apply_rewards`) **в той же транзакции**;
  4. пишут строку лога шага (`choice_logs`) и коммитят.
- В `choice_logs` уникальный индекс `(attempt_id, step)`: если два запроса всё-таки проскочили одновременно,
  второй упадёт на вставке и откатится целиком (`_commit_step` превращает это в `step_mismatch`).

Итог: шаг и награды применяются ровно один раз при любых двойных кликах и параллельных вкладках. Это проверено
тестом, где 8 потоков одновременно отправляют один шаг (`tests/test_concurrency_pg.py`).

## 8. Награды, компетенции, рекомендации

**Награды** — `backend/app/services/rewards.py`, правила — `backend/app/gamification/rules.py`:
- сырой результат = (лояльность + безопасность) / 2 на финале; **результат рейса** — его место между худшим (0) и
  лучшим (100) возможным исходом сценария (`scenarios/scoring.py`: обход всех состояний), так что идеал = 100;
- лучший результат по каждому сценарию хранится в `scenario_bests`; **опыт = сумма лучших результатов**, поэтому
  повтор даёт только прирост (в демо: 50 → 0 → 100 даёт +50, 0, +50);
- уровни: 0 / 50 / 120 / 200 / 300 опыта;
- достижения: `first_trip` (правило сервера), `diplomat` и `safe_passage` (условия `awards` в данных сценария) и
  свои достижения сценария (`graph.achievements`, придумываются в редакторе); каждое выдаётся один раз;
- уведомления: новый уровень, достижение, публикация сценария.

**Компетенции** — `backend/app/services/competency.py`, список — `backend/app/gamification/competencies.py`:
коммуникация, безопасность, первая помощь, стрессоустойчивость (учебный показатель для шагов с таймером).
В профиле берётся **последнее** завершённое прохождение каждого сценария, суммы «набрано» и «максимум» → процент.
Нет оценённых решений — «нет данных». Слабая — наименьшая ниже 100%.

**Рекомендация** (`_recommend`) по тегам сценариев: первый рейс → непройденный сценарий на слабую компетенцию →
любой непройденный → повтор с конкретной целью.

Подробные формулы — [scoring.md](scoring.md).

## 9. Остальной бэкенд

- **Вход** — `services/auth.py`, `api/auth.py`, `api/deps.py`. Пароли — PBKDF2 (`core/security.py`). При входе
  создаётся случайный токен → в cookie `vsm_session` (HttpOnly), в таблицу `auth_sessions` — только его хэш.
  `current_user` достаёт сотрудника из сессии; `methodologist` дополнительно проверяет роль. После 5 неверных
  паролей логин блокируется на 60 секунд.
- **Профиль, история, рейтинг, уведомления** — `services/profile.py`, роуты в `api/me.py`. Рейтинг отдаёт только
  отображаемые поля.
- **Редактор** — `services/editor.py`, `api/editor.py`. У сценария есть опубликованная версия и черновик
  (`scenarios.draft`). Черновик сохраняется даже с ошибками (ответ перечисляет их), публикация проверяет
  валидатором, повышает версию и рассылает уведомления.
- **Валидатор** — `scenarios/validator.py`, функция `collect_errors`: типы и обязательные поля, опечатки,
  ссылки на узлы, диапазоны, условия, достижимость узлов и путь к финалу. Возвращает все ошибки с путями.
- **Визуал** — `scenarios/visual.py`: вычисляет фон, кто в кадре (правила `cast` с позой и местом), какое у них
  настроение (правило из данных или по лояльности) и какие предметы видны. Наружу уходит только результат, без условий.
- **Интеграция HR/LMS** — `api/integrations.py`, по ключу `X-API-Key`.
- **Ошибки** — `scenarios/errors.py` (`ScenarioError` с кодом) и `api/errors.py` (код → HTTP-статус).
- **Время** — `core/clock.py`: `current_time` — зависимость FastAPI, в тестах подменяется, поэтому таймеры
  проверяются точно.

## 10. Фронтенд

**Маршруты** (`frontend/src/App.tsx`): `/login`, `/` (главная), `/scenarios`, `/attempts/:id` (прохождение),
`/attempts/:id/result` (разбор), `/profile`, `/leaderboard`, `/editor`, `/editor/:id`.

**Запросы** — `src/api/client.ts` (fetch с cookie, разбор ошибок в `ApiError` с `code`), `src/api/endpoints.ts`,
`src/api/editor.ts`, типы — `src/api/types.ts`.

**Вход** — `src/auth/AuthContext.tsx`: при старте спрашивает `/auth/me`; любой ответ 401 возвращает на `/login`.

**Прохождение** — самая важная часть, хук `src/hooks/useAttemptPlay.ts`:
- состояние всегда берётся с сервера: загрузка по `attempt_id` из адреса, перечитывание при возврате на вкладку и
  при восстановлении сети;
- каждый выбор отправляется с `expected_step`; пока запрос идёт, кнопки заблокированы;
- таймер: «осталось» = `deadline − server_time` из ответа, дальше уменьшается по `performance.now()` (часы
  устройства не используются);
- на нуле клиент один раз шлёт «время вышло»; если сервер ответил, что рано, — через секунду перечитывает
  состояние (без бесконечного цикла);
- `step_mismatch` → перечитать; ошибка сети → сообщение и кнопка «Обновить состояние».

Страница `src/pages/PlayPage.tsx` рисует шкалы, сцену, таймер, реакцию на последний шаг, текст и кнопки
(клавиши 1–9 тоже работают).

**Сцена** — `src/scene/CarriageScene.tsx` (вагон, окна, кресла, чемодан, лужа), `src/scene/Figure.tsx`
(фигуры и лица для 6 настроений). Данные сцены приходят от сервера в `node.visual`; без них рисуется пустой вагон.

**Остальные страницы**: главная (уровень, рекомендация, компетенции), каталог, разбор (награды, компетенции, шаги),
профиль, рейтинг, редактор. Общие куски: `components/` (шапка с уведомлениями, шкала, прогресс, состояния
загрузки/ошибки/пусто, граница ошибок).

**Редактор** — `src/pages/EditorPage.tsx` + `src/editor/`: `GraphSettings` (настройки сценария), `NodeEditor`
(узел), `OutcomeEditor` (эффекты, флаги, оценки, переходы), `ConditionBuilder` (условия строками
«поле — оператор — значение»), `VisualEditor` (метаданные сцены), `graphOps.ts` (переименование узла с правкой
ссылок, перевод условий в форму и обратно — покрыто тестами).

**Стили** — один файл `src/styles.css`, палитра в переменных в начале файла (тёмно-синий `#14243A`,
молочный `#F4F6F8`, бирюзовый `#25B5AD`, янтарный, красный).

## 13. Демо-данные

`python -m app.seed` (в Docker запускается сам):
- загружает сценарии из `data/*.json` (если методист переопубликовал встроенный сценарий в редакторе, seed его не
  трогает);
- создаёт аккаунты: `provodnik` (чистый профиль), `metodist`, пятеро синтетических коллег;
- проигрывает для коллег заранее заданные пути через настоящий движок — чтобы рейтинг не был пустым;
- повторный запуск ничего не дублирует. Пароль всех демо-аккаунтов — `DEMO_PASSWORD` (по умолчанию `vsm-demo`).

## 14. Запуск и тесты

```bash
docker compose up --build          # http://localhost:8080, Swagger — http://localhost:8000/docs
docker compose down -v             # полная очистка данных
```

Без Docker и тесты — см. README. Основные команды:

## 15. Типовые правки (для «живого изменения»)

| Хочу… | Где и как |
|---|---|
| изменить текст, эффект или развилку | редактор методиста, либо JSON в `backend/app/scenarios/data/` + `python -m app.seed` (версия вырастет) |
| изменить порог финала «Места у окна» | `window_seat.json`, условие `{"scale": "loyalty", "op": "<", "value": 70}` в трёх переходах к финалам |
| добавить сценарий | создать в редакторе или положить новый JSON в `data/` и выполнить seed; валидатор подскажет ошибки |
| добавить достижение | без кода — «Свои достижения» в редакторе (`graph.achievements`); встроенное — `ACHIEVEMENTS` в `gamification/rules.py` и условие `awards` в данных сценария |
| поменять уровни | `LEVELS` в `gamification/rules.py` |
| поменять формулу результата | `attempt_score` / `normalized_score` в `scenarios/scoring.py` (и обновить `docs/scoring.md`) |
| добавить компетенцию | `COMPETENCIES` в `gamification/competencies.py`, подписи — `frontend/src/utils/labels.ts` и `editor/OutcomeEditor.tsx` |
| поменять цвета | переменные в начале `frontend/src/styles.css` |
| новое поле в таблице | модель в `models/models.py` + новая миграция в `migrations/versions/` (тест `test_migrations` сверяет их) |

После правки кода — запустить тесты. Если меняли JSON сценария — пройти его в интерфейсе или проверить тестом.

## 16. Словарь

- **Попытка (attempt)** — одно прохождение сценария сотрудником.
- **Шаг (step)** — одно применённое решение или тайм-аут; нумеруются с 1.
- **Узел (node)** — ситуация в сценарии; **финал** — узел с `is_ending`.
- **Исход (outcome)** — то, что происходит после варианта или тайм-аута: эффекты, флаги, переход.
- **Флаг** — отметка «игрок это сделал», влияет на условия дальше.
- **Снимок (snapshot)** — копия графа в попытке; защищает её от правок сценария.
- **Черновик / публикация** — правки методиста до и после выпуска новой версии.
- **Синтетические данные** — сгенерированные результаты вымышленных коллег, помечены в интерфейсе.
