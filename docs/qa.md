# Вопросы жюри: ответы и где смотреть код

Шпаргалка для защиты. К каждому ответу — место в коде, которое стоит уметь открыть и объяснить.

## Движок сценариев

**Как устроен сценарий?**
JSON-граф: узлы с текстом, вариантами, необязательным таймером и исходом тайм-аута; варианты несут эффекты на шкалы,
флаги, оценки компетенций, объяснение и переход (`next_node` или список условных `transitions`). Формат —
[scenario-format.md](scenario-format.md), данные — `backend/app/scenarios/data/*.json`.

**Что происходит при нажатии на вариант?** `ScenarioEngine.apply_choice` — `backend/app/scenarios/engine.py:86`.
По порядку: попытка не завершена и `expected_step` совпадает → если дедлайн наступил, применяется тайм-аут, иначе ищется
**видимый** вариант → оценка компетенций (`_assess`, стр. 128) → эффекты с ограничением 0–100 → флаги → следующий узел
(`_next_node`, стр. 119) → шаг +1, таймер нового узла стартует (`_apply_outcome`, стр. 151).

**Почему условия — JSON, а не код или `eval`?** Безопасность (данные методиста не исполняются) и проверяемость:
валидатор знает все формы условий. Интерпретатор — 20 строк: `evaluate`, `backend/app/scenarios/conditions.py:35`.

**Условия выбора и переходов проверяются на одном и том же состоянии?** Нет. Видимость варианта — на состоянии **до**
шага, условный переход — **после** эффектов и флагов этого шага. Так порог «лояльность ≥ 70» учитывает и последнее решение.

**Как не дать опубликовать сломанный сценарий?** `collect_errors`, `backend/app/scenarios/validator.py:41`: типы, опечатки
в полях, ссылки на узлы, диапазоны, флаги, условия, достижимость каждого узла и путь к финалу (`check_paths`, стр. 366).
Ошибки возвращаются списком с путями, например `nodes.start.choices[0].next_node: points to unknown node 'x'`.

## Таймер

**Почему таймер на сервере?** Клиенту нельзя доверять часы. Дедлайн = время показа узла + `timer_seconds`
(`deadline`, `engine.py:74`); граница — `now ≥ deadline`. Выбор после дедлайна засчитывается как тайм-аут.

**Что будет, если закрыть вкладку на критическом шаге?** При возврате `GET /attempts/{id}` применяет просроченный
тайм-аут ровно один раз (`expire_if_due`, `engine.py:112`; `get_attempt`, `backend/app/services/attempts.py:96`).

**Как фронтенд считает оставшееся время?** `deadline − server_time` на момент ответа, дальше — монотонные часы
`performance.now()`. Если клиент отправил тайм-аут раньше сервера (409 `timer_not_expired`), повтор идёт не чаще раза в
секунду через `GET`: `frontend/src/hooks/useAttemptPlay.ts`, константа `RESYNC_AFTER_EARLY_TIMEOUT_MS`.

## Надёжность

**Двойной клик или два запроса одновременно?** Три уровня: кнопки блокируются на время запроса; сервер сверяет
`expected_step` (409 `step_mismatch`); строка попытки блокируется `SELECT … FOR UPDATE` (`_lock_attempt`,
`attempts.py:29`), а лог шага имеет `UNIQUE(attempt_id, step)` — дубль откатывается целиком (`_commit_step`, стр. 63).
Проверено тестом настоящей гонки восьми потоков на PostgreSQL (`backend/tests/test_concurrency_pg.py`).

**Что если методист изменит сценарий, пока кто-то его проходит?** Попытка хранит снимок графа, названия и версии;
движок читает только снимок. Публикация (`publish`, `backend/app/services/editor.py:122`) повышает версию.

## Очки, опыт, достижения

**Как считается опыт и почему его нельзя накрутить?** Результат рейса = среднее двух шкал на финале; опыт = сумма лучших
результатов по сценариям, поэтому повтор даёт только прирост. `apply_rewards`, `backend/app/services/rewards.py:28`,
формулы — [scoring.md](scoring.md).

**Почему награды не начисляются дважды?** Они записываются в той же транзакции, что и финальный шаг, а шаг фиксируется
один раз (см. выше); плюс блокировка строки сотрудника и уникальный индекс на достижения.

**Как задаётся «Дипломат»?** В данных сценария: `awards` с условием на флаги, проверяется на итоговом состоянии.
Идентификаторы достижений — `backend/app/gamification/rules.py`.

## Компетенции и рекомендации

**Как считается компетенция?** В каждом шаге: набрано / максимум среди **видимых** вариантов (`_assess`). В профиле —
последнее завершённое прохождение каждого сценария (`latest_finished_per_scenario`, `backend/app/services/competency.py:15`),
поэтому повторы не накручивают оценку. Нет оценённых решений — «нет данных».

**Откуда рекомендация?** Правила по тегам опубликованных сценариев: `_recommend`, `competency.py:49`.

## Доступ и данные

**Кто есть кто?** Роль и личность — только из серверной сессии (`current_user`, `backend/app/api/deps.py:15`).
Чужие попытки — 404, редактор — методисту (`methodologist`, стр. 23). Пароли — PBKDF2, в cookie — случайный токен,
в БД — его SHA-256; блокировка после 5 неверных паролей (`sign_in`, `backend/app/services/auth.py:15`).

**Персональные данные?** Только вымышленные сотрудники; синтетические результаты помечены; секреты — из окружения.

## Предметная область

**На чём основаны сценарии?** На материалах кейса — примерах ситуаций взаимодействия поездного персонала с пассажирами:
«Место у окна» — ситуации № 8, 13, 14; «Пассажиру стало плохо» — № 19, 28, 29. Уроки разбора используют ролевую модель
«признать ситуацию → обозначить правило → предложить решение → заверить». Обращение к начальнику поезда не штрафуется —
в материалах это рекомендованная реакция во многих ситуациях.

## Живое изменение (отрепетировать)

1. **Порог финала.** В `backend/app/scenarios/data/window_seat.json` в условии
   `{"scale": "loyalty", "op": "<", "value": 70}` заменить 70 на 75 во всех трёх переходах к финалам
   (порог безопасности рядом не трогать), выполнить `docker compose exec backend python -m app.seed` (или `python -m app.seed` локально) —
   версия сценария вырастет; путь «спокойно → убрать самому → пересадить без проверки → проверить → тактично →
   проводить» (лояльность 70) теперь даёт «Разрешено с недовольством».
2. **Новая развилка без кода.** Методист → «Редактор» → узел → «+ вариант (развилка)» → текст и следующий узел →
   «Сохранить и проверить» → «Опубликовать». Показать, что ссылка на несуществующий узел подсвечивается ошибкой.
3. **Правило шкалы.** Поменять `effects` у варианта в редакторе и пройти сценарий заново — разбор покажет новое
   фактическое изменение.
