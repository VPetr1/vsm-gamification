# Геймификация для ВСМ — Backend

Бэкенд обучающего приложения для проводников ВСМ-400: движок нелинейных сценариев
с таймерами, флагами и условными переходами, двойная шкала «лояльность пассажира» /
«рейтинг безопасности», хранение попыток, истории решений и разбор результата.

Встроенные сценарии: «Конфликт из-за откинутого кресла» (демо) и «Место у окна» (13 узлов, 3 финала).

Данные синтетические, реальных ПДН пассажиров и сотрудников в репозитории нет.

## Архитектура

```
frontend (React, отдельная команда)
        │  HTTP/JSON
        ▼
backend/app
 ├── api/           — FastAPI-роуты (employees, scenarios, attempts) и маппинг кодов ошибок в HTTP
 ├── services/      — сценарии использования попытки: блокировка строки, движок, лог шага, результат
 ├── scenarios/     — движок: engine.py, conditions.py (условия без eval), validator.py
 │   └── data/      — встроенные сценарии в JSON (тексты, эффекты, объяснения)
 ├── models/        — SQLAlchemy-модели (Employee, Scenario, Attempt, ChoiceLog)
 ├── schemas/       — Pydantic-схемы запросов/ответов
 └── core/          — конфиг, БД, часы запроса
backend/migrations — Alembic (0001 базовая схема … 0004 снимки сценариев)
        │
        ▼
   PostgreSQL (граф сценария — JSON; попытка хранит неизменяемый снимок графа)
```

Модульность: движок сценариев (`app/scenarios/engine.py`) не знает про FastAPI/HTTP
и не знает про конкретный сценарий — весь контент задаётся JSON-графом
(см. [docs/scenario-format.md](docs/scenario-format.md)). Новый сценарий добавляется
JSON-файлом в `app/scenarios/data/` или через `POST /scenarios` без изменения кода движка.
Порядок применения эффектов и проверки переходов описан в
[docs/scenario-format.md](docs/scenario-format.md#порядок-применения-шага), API для интерфейса —
в [docs/frontend-api.md](docs/frontend-api.md).

### Последовательность одного шага (`POST /attempts/{id}/choice`)

```
Клиент → API: {choice_id | null, expected_step}
Service: SELECT attempt FOR UPDATE (параллельные запросы к попытке выстраиваются в очередь)
Engine:  статус и expected_step → 409 при несовпадении
Engine:  now >= deadline ? timeout узла : видимый вариант (условие на состоянии до шага)
Engine:  effects → clamp 0..100 → set_flags → переход (next_node | первый подходящий transition)
Engine:  step += 1, таймер нового узла стартует; финал завершает попытку
Service: INSERT choice_logs(attempt_id, step, …) UNIQUE → COMMIT (дубль шага откатывается целиком)
API → Клиент: состояние (узел, шкалы, step, deadline, server_time, last_step)
```

## Локальный запуск

### Через Docker (рекомендуется)

```bash
docker compose up --build
```

API поднимется на `http://localhost:8000`. При старте контейнер выполняет миграции
(`python -m app.db_upgrade`), затем загружает встроенные сценарии и синтетического сотрудника
(`python -m app.seed`).
Интерактивная документация API (Swagger UI): `http://localhost:8000/docs`.

### Без Docker

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# нужен запущенный PostgreSQL, доступный по DATABASE_URL
export DATABASE_URL=postgresql://vsm:vsm@localhost:5432/vsm

python -m app.db_upgrade   # миграции Alembic до последней версии
python -m app.seed         # встроенные сценарии + синтетический сотрудник
uvicorn app.main:app --reload
```

### Миграции

Схема ведётся Alembic (`backend/migrations`). `python -m app.db_upgrade` обновляет базу до последней
ревизии; базу, созданную ранней версией проекта через `create_all` (без таблицы `alembic_version`), он
сначала помечает базовой ревизией `0001`, поэтому существующие данные сохраняются и дозаполняются
(номера шагов, флаги, снимки сценариев для уже начатых попыток).

| ревизия | что меняет |
|---|---|
| 0001 | базовая схема (как у `create_all` ранней версии) |
| 0002 | `attempts.step`; в `choice_logs`: `step`, `next_node`, значения шкал после шага, `UNIQUE(attempt_id, step)` |
| 0003 | `attempts.flags` |
| 0004 | `scenarios.version`, `attempts.scenario_version`, `attempts.graph_snapshot` |

### Тесты

```bash
cd backend
source .venv/bin/activate
python -m pytest -v
```

Основной набор не требует внешних сервисов: API-тесты поднимают FastAPI поверх SQLite in-memory,
время запроса подменяется, поэтому таймеры проверяются точно на границе `now >= deadline`. Миграции
проверяются на SQLite (схема после `upgrade` сравнивается с моделями, данные старой схемы дозаполняются).

Тест настоящей гонки параллельных запросов требует Postgres и запускается только на отдельной базе,
имя которой оканчивается на `_test` (её схема пересоздаётся):

```bash
TEST_DATABASE_URL=postgresql://vsm:vsm@localhost:5432/vsm_test python -m pytest tests/test_concurrency_pg.py -v
```

## API (кратко)

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/employees` | создать сотрудника |
| GET | `/employees` | список сотрудников |
| POST | `/scenarios` | создать сценарий (валидирует граф) |
| GET | `/scenarios` | список сценариев |
| POST | `/attempts` | начать попытку прохождения сценария → первый узел |
| GET | `/attempts/{id}` | текущее состояние; догоняет истёкший таймер |
| POST | `/attempts/{id}/choice` | `{choice_id, expected_step}`; `choice_id: null` после дедлайна — тайм-аут |
| GET | `/attempts/{id}/result` | разбор завершённой попытки: решения, фактические изменения шкал, объяснения, финал |

Полная спецификация — автогенерируемый OpenAPI/Swagger на `/docs` и `/openapi.json`
запущенного сервиса; примеры запросов и ответов для интерфейса — [docs/frontend-api.md](docs/frontend-api.md).

## Пример пользовательского сценария (User Flow)

1. Проводник открывает каталог (`GET /scenarios`) и выбирает «Место у окна».
2. `POST /attempts` создаёт попытку со шкалами 60/80 и возвращает первый шаг без таймера.
3. Проводник выбирает вариант: `POST /attempts/{id}/choice` с `expected_step`. Следующий шаг
   (чемодан в проходе) критический: 20 секунд, интерфейс отсчитывает `deadline − server_time`.
4. Если время вышло, клиент шлёт `choice_id: null`, и применяется ветка тайм-аута: пассажирка
   спотыкается. Если страницу перезагрузили, `GET /attempts/{id}` сам применит истёкший тайм-аут.
5. Дальше: проверка билетов (или пустое обещание / пересадка без проверки), выяснение ошибки в номере
   вагона, разрешение конфликта. Финал зависит от флагов поведения (резкость, игнорирование, обещание,
   свободный проход) и порога шкал ≥ 70: спокойное разрешение, разрешение с недовольством или передача
   конфликта начальнику поезда.
6. `GET /attempts/{id}/result` показывает разбор: каждое решение, фактические изменения шкал,
   объяснение и урок шага.

Точные запросы и ответы — в [docs/frontend-api.md](docs/frontend-api.md).

## Ограничения текущей версии и план развития

Сделано ядро: движок сценариев (таймеры, флаги, условные переходы), защита от двойного применения шага,
снимки сценариев, строгий валидатор, разбор результата, два сценария, миграции.

Пока нет (следующий слой поверх ядра, `engine.py` не меняется): профиль/уровни/опыт, достижения, таблица
лидеров, уведомления, агрегированная аналитика по компетенциям, авторизация, редактор сценариев и
эндпойнт изменения сценария (версионирование и снимки для него уже готовы), React-интерфейс.

## Безопасность и данные

- В демо используются только синтетические данные (`app/seed.py`, `app/scenarios/data/*.json`) —
  реальных ПДН пассажиров и сотрудников нет.
- Секретов и ключей в репозитории нет; `DATABASE_URL` берётся из окружения.
- Клиенту не отдаются эффекты, условия, переходы и объяснения до завершения попытки; скрытый вариант
  нельзя выполнить по id.
